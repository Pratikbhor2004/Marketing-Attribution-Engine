# How I used AI on this project

**Summary:** I used Claude Code (Anthropic, in VS Code) as the main implementation engine. I set the scope, made the
product decisions and fixed the quality bar the work had to meet. The AI wrote most of the code, tests and documentation.
Everything is checked by an automated evidence chain anyone can re-run: tests, 111 data checks, scoring against ground
truth, money reconciliation and a reproducibility proof. The verbatim prompts are in [PROMPT_HISTORY.md](PROMPT_HISTORY.md).

The repository's first commit (`0533110`, 10 Nov) is an earlier version of the engine that existed before this session.
*[AUTHOR: say how that version was produced.]* The session's first job was to review it, and it found three real defects:

1. **Labels leaked into the inputs.** The input tables carried `issue_type`, and the engine filtered on it, so it was "detecting" anomalies by reading the answer key.
2. **Outcomes were random.** Win/loss was assigned independently, which the brief forbids ("generate outcomes … from documented rules").

## 2. Where AI accelerated the work
* **Boilerplate at scale:** 58 API endpoints, a 70-request Postman collection generated from the OpenAPI spec, a data dictionary for 23 tables, and Mermaid diagrams.
* **Vectorised pandas** for 200k touchpoints and 10k opportunities: a full-scale run takes about 46 s.
* **Documentation from code:** the Postman collection, OpenAPI files, Swagger page and data dictionary are generated by scripts, so they can't drift from the code.
* **Consistency checks** that would be tedious by hand, such as a test that fails if any endpoint is missing from Postman or Swagger.

## 3. Where I relied heavily on AI
I'm stating this plainly:
* **Domain modelling details:** the eligibility rules E1–E6, the logistic win rule with per-channel effects, largest-remainder cent allocation, and the total-variation-distance and Spearman evaluation metrics.
* **Nearly all implementation and test code.**
* **Debugging.** The AI found and fixed its own defects during the build. Each was caught by a test or validation check, not by luck:

| Defect the AI introduced | How it was caught | Fix |
|---|---|---|
| Dates came out as 1970 (pandas 3 changed the default datetime unit) | Date-range validation checks failed | Pinned timestamps with `.as_unit("ns")` |
| ROI of about −90% for every campaign (budgets not scaled to revenue) | Sanity review of the ROI distribution | Scaled spend to deal volume |
| SQLite connection never closed, which locked the database on Windows | Regeneration failed in the test suite | A `connect()` context manager that closes the connection |
| Reconciliation broke for runs with only some models | API test for custom runs | Reconcile only the models present in the run |
| Validation failed after events were appended through the API | API lifecycle test | Validate the generated baseline and live events separately |
| Opportunity stage filter read the generation snapshot, not the live stage | API test | Filter on the `opportunity_current_stage` view |
